# MVP: правила запису на прийом

Документ фіксує домовленості до початку реалізації бронювання. Коду бронювання в репозиторії ще немає.

## Правила

### Заявка пацієнта

- Пацієнт подає заявку через публічний сайт без акаунта і без авторизації.
- Поля заявки:

| Поле | Обов'язкове | Примітка |
| --- | --- | --- |
| Ім'я | так | |
| Прізвище | так | |
| По батькові | ні | |
| Телефон | так | |
| Email | див. відкрите рішення 1 | використовується для сповіщень |
| Канал зв'язку | так | вибір зі списку, див. відкрите рішення 2 |

### Статуси

- Публічна заявка створюється зі статусом `PENDING` і **не займає слот**: цей час лишається доступним для інших заявок і записів.
- Запис, створений персоналом, одразу має статус `CONFIRMED`.
- Слот займає лише запис у статусі `CONFIRMED`.

### Перетини

- Підтверджені прийоми одного лікаря не можуть перетинатися в часі.
- Правило має виконуватись і тоді, коли персонал підтверджує заявки одночасно. Тому перевірки в коді застосунку недостатньо, гарантію дає база даних.
- Наслідок: на один і той самий час може існувати кілька заявок `PENDING`. Підтвердити вдасться лише одну, решту персонал переносить або відхиляє.

### Розклад і час

- Кілька лікарів, у кожного свій розклад.
- Послуги мають різну тривалість, тривалість прийому залежить від послуги.
- Розклад підтримує винятки (відпустка, лікарняний, скорочений або додатковий робочий день).
- Календар показує час у часовому поясі `Europe/Kyiv`.

## Пропозиція реалізації (підтвердити в задачі бронювання)

- **Перетини.** Обмеження в PostgreSQL: `EXCLUDE USING gist (doctor_id WITH =, tstzrange(starts_at, ends_at, '[)') WITH &&) WHERE (status = 'CONFIRMED')` з розширенням `btree_gist`. Prisma schema такого не описує, тому обмеження додається SQL-кодом у міграції. Порушення (код `23P01`) API перетворює на `409 Conflict`. Інтервал напіввідкритий, тож прийоми впритул один за одним дозволені.
- **Час.** Моменти початку й кінця зберігаються як `timestamptz` (UTC), API віддає ISO 8601. Робочі години лікаря зберігаються як локальний час `Europe/Kyiv` і переводяться в UTC під час розрахунку слотів, інакше розклад зсувався б на годину при переході на літній та зимовий час.

## Відкриті рішення

Кожне з них змінює схему БД або контракт API, тому їх треба закрити до задачі бронювання.

1. **Чи email обов'язковий?** Якщо ні, колонка nullable і потрібен запасний спосіб сповіщення (наприклад, SMS чи дзвінок). Якщо так, частина пацієнтів без email не зможе подати заявку онлайн.
2. **Які канали зв'язку у списку?** Кандидати: дзвінок, SMS, Viber, Telegram, WhatsApp, email. Від відповіді залежить, чи це enum у схемі, чи довідник в адмінці, і чи канал потребує окремого ідентифікатора (нік у Telegram не збігається з телефоном).
3. **Що саме обирає пацієнт?** Конкретного лікаря чи «будь-якого», точний слот чи бажаний день. Від цього залежить, чи `doctorId` і час у заявці `PENDING` обов'язкові.
4. **Повний набір статусів і переходів.** Окрім `PENDING` і `CONFIRMED` потрібні щонайменше скасування та відхилення. Чи потрібні `COMPLETED` і `NO_SHOW`? Чи заявка `PENDING` застаріває сама?
5. **Пацієнт як окрема сутність.** Чи заявки одного пацієнта об'єднуються в картку (наприклад, за телефоном), чи контактні дані зберігаються лише в заявці. Це визначає модель даних CRM.
6. **Формат телефону.** Чи приймаємо лише українські номери і чи зберігаємо в E.164 (`+380...`).
7. **Тривалість послуги.** Одна на послугу чи може відрізнятися в різних лікарів. Чи один прийом може містити кілька послуг і чи потрібна пауза між прийомами.
8. **Згода на обробку персональних даних і захист форми.** Чи зберігаємо факт і час згоди в заявці, який захист від спаму потрібен публічному endpoint (rate limit, captcha).
